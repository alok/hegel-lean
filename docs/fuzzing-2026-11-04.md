# November 4, 2026 self-hosted fuzzing pass

Hegel generated the inputs for testing its own Lean frontend. Two new executables
hold the fuzzers, and CI runs a short smoke campaign of each.

- `lake exe hegel_fuzz [seeds] [examples] [prefix]` checks 21 contract properties. They
  cover replay-token round trips and decode stability, `diffLines` reconstruction,
  `diffRepr` content preservation, the two's-complement integer codec, duration rounding,
  URI parse/render stability, and the bounds of every standard generator. It then runs 37
  invalid-configuration probes. Each probe must fail without crashing, hanging, or
  reaching an internal engine error.
- `lake exe hegel_fuzz_harness [start] [count] [examples]` uses a seeded SplitMix64 PRNG
  to build random generator programs from 24 combinators. These include filters,
  `mapMaybe`, dependent binds, unique collections, sets, entries, custom collections with
  rejection, recursion, regexes, Unicode categories, and floats. Each program runs under a
  random property shape: plain assertion, `assume`, `target`, or several failure origins.
  A valid program must never produce an engine error. Every counterexample must replay
  three times with the same origin and annotations, and must reproduce through an encoded
  replay token. Passing `machines` as a fourth argument fuzzes random state machines
  instead. Each machine has one to four weighted rules (push a generated value, pop, pop
  under `assume`, clear, or a buggy assertion), an optional invariant, and a random step
  count. The same no-error and replay checks apply.

| Campaign | Size | Result |

| Contract properties | 21 properties × 20 seeds × 1,000 examples, then × 50 seeds × 2,000 | 2 bugs, both fixed |
| Invalid-configuration probes | 37 probes | 0 crashes after fixes |
| Random generator programs | 25,800 programs × 100–150 examples | 0 bugs |
| Random state machines | 4,700 machines × 50–100 examples | 0 bugs |
| Random programs with concurrent shapes | 4,000 programs × 100 examples | 1 slowdown and 1 flaky-fork hazard, both handled |
| Float bound grid | 16,928 bound/flag/width configurations | 0 internal errors after the fix |

## Bugs fixed

1. **Empty float ranges aborted the engine.** `Gen.float { min := 0.0, max := -0.0 }`
   failed with libhegel `Internal error … FloatChoice::simplest: no valid float for this
   choice`. The engine orders `-0.0` before `+0.0`, so that range is empty. Infinity-only
   ranges with infinities disallowed failed the same way. One example is
   `[1.7976931348623157e308, ∞]` with an exclusive minimum. `Gen.float32` and the typed
   float builders were affected too. The builder already caught the plain `[+0, -0]` case,
   but it missed exclusive bounds that step onto a disallowed infinity.
   `Gen.FloatConfig.emptyReason?` now rejects these before the native call. Exclusive
   bounds step in the requested width. Plain `Gen.float` reports an error, like the engine's
   own invalid-argument handling. `Gen.float32` and the builders report a
   `generator/float*` configuration failure. A 5,408-configuration grid regression
   confirms that no special-value bound reaches the internal error.
2. **A NUL byte in a failure origin turned the whole campaign into an engine error.**
   The C API takes origins as NUL-terminated strings, so `failure "a\x00b"` reported
   `Embedded NUL in C-string argument` and lost the counterexample. Such origins, and
   any origin that already begins with the escape prefix, now cross the boundary as
   hex-encoded UTF-8 behind the prefix `\x1bhegel-origin:`. They are decoded when the
   engine returns them. All other origins pass through unchanged. The regression uses
   three origins: a NUL origin, its literal escaped spelling, and a malformed escape.
   It checks that they stay distinct and byte-exact through shrinking, replay, and
   replay tokens.

The C bridge's embedded-NUL error now names the argument it rejected, such as `origin`,
`label`, or `name`. The `Alphabet` docstring now states that a character cannot be both
included and excluded. It used to say inclusion was applied before exclusion, but the
engine rejects such overlaps.

## Concurrency follow-up

The program fuzzer now also runs each generator under three concurrent shapes: a fork
joined after a parent draw, `Branch.mapConcurrently`, and `Branch.concurrently`. This
found two problems.

1. **Fork and branch joins were slow.** A parent waiting on a child polled with
   `IO.sleep 1`, so every join cost at least a millisecond even when the child finished in
   microseconds. 300 examples with one fork took about 380 ms, against 1 ms without the
   fork. The wait loops now spin for the first 200 µs before they fall back to sleeping.
   The same run takes about 27 ms, and a four-way `mapConcurrently` dropped from about
   400 ms to about 120 ms. Cancellation still propagates at every poll.
2. **A fork left unjoined when its parent fails makes shrinking flaky.** If the parent
   fails or a parent draw aborts before `Fork.join`, the property cancels the fork, but
   cancellation is cooperative. Whether the child made its next draw first depends on
   thread timing, so the recorded choices differ between runs and the report can say
   "Flaky". With 40 seeds, 2 to 4 seeds hit this. Waiting for the child instead would hang
   children that loop until cancelled, so the behavior stays. `Fork.spawn` now documents the
   hazard and the fix: join the fork before rethrowing. A 40-seed regression in
   `Tests/Concurrency.lean` checks that pattern, and fails within one run without the join.

## Observed and left unchanged

- `Gen.text` passes code-point bounds above `0x10ffff` to the engine, which clamps them.
  `Alphabet.text` rejects such bounds instead.
- Plain generators report invalid configurations as errors, while builders, `Gen.float32`,
  and `Alphabet.text` report them as `generator/*` configuration failures. Both outcomes
  are non-passing. This fix keeps each generator's existing convention.
- The libhegel internal error is an upstream engine bug. The frontend now avoids it.
